# hik-get-dumber — 调研稿 → 总经理决策稿

把「写对、写全」的工程师/预研长文，改成「能拍板、能复述」的短决策备忘录。  
**允许大刀阔斧删改结构；允许为决策补新表、新尺子、新锚点。**  
主题不绑定某一产品线；具体内容以用户当前文稿为准。

与 `hik_report` 的分工：`hik_report` 管论证文风与汇报注解；本 skill 管**读者降维与决策重构**。需要 DOCX 时再走 `md-to-docx-report`。

---

## 1. 默认读者与成功标准

| 维度 | 源稿（工程师） | 目标稿（总经理） |
| --- | --- | --- |
| 问题 | 这件事到底是什么、证据全不全 | 我们选哪条路、花多少、站在哪、还差什么 |
| 长度 | 可附录级长文 | 一次翻完（默认目标：**源稿字数的 10%–25%**，或 ≤ 正文约 2000–4000 汉字，以较短者为准；用户另有指定则从其指定） |
| 主载体 | 定义链、数据集、字段、论文/开源 | **主张一句 + 对照表 + 自家/行业锚点** |
| 术语 | 准确优先 | **可对外复述的业务词优先**（必要时括号保留原术语一次） |
| 对错感 | 论证完备 | **选型可执行**；探索项保留位置但不抢主路径 |

成功标准：总经理读完能口头带走——**主张、依据数字、代价、边界、下一步**。

---

## 2. 改造权限（必须遵守的心态）

1. **砍不是失败**：数据集考古、schema、代码字段、多项目罗列、教学小故事，默认进「附件/答问备用」，不进主文。
2. **改不是篡改事实**：可改结构、标题、比喻、对照轴；**不可编造**原文没有的成功率、节拍、人天、客户结论。缺数时写「待补」或向用户要数，不要假装有数。
3. **加是为决策服务**：允许新增——选型对照表、分级/阶段尺、人天·周期·节拍列、产品在谱系中的位置、三条以内「为何选这条」的理由。新增框架必须能装下原文已有证据。
4. **跳出对错辩论**：不证明源稿「错了」；只证明目标稿**更服务拍板**。源稿价值是原料库，不是交付形态。

---

## 3. 工作流

复制进度并执行：

```
hik-get-dumber:
- [ ] 1. 定位源稿主张与可带走决策（没有主张则先推断 1 句，标「拟定」）
- [ ] 2. 列出必删 / 必留 / 必补
- [ ] 3. 按默认骨架重写主文（可大改章节名与顺序）
- [ ] 4. 注入决策数字与产品锚点（无则标待补）
- [ ] 5. 自检：去掉附录后，主张是否 30 秒可复述
- [ ] 6. 若用户要 docx → md-to-docx-report
```

### Step 1 — 抽出决策核

从源稿用 5 行以内写下：

- **主张**（我们倾向什么）
- **对照轴**（和什么比：两条技术路线 / 买与建 / 阶段 A vs B）
- **硬数字**（成功率、节拍、周期、人力、成本、样本规模……原文有的才写）
- **边界**（现在不承诺什么）
- **下一步**（验证、采购、试点、继续盯前沿）

若源稿只有百科没有主张：根据证据**拟定**一条务实主张，在文首或回复里标明「主张为改写拟定，请确认」。

### Step 2 — 必删 / 必留 / 必补

| 类型 | 处理 |
| --- | --- |
| 必删出主文 | 多数据集逐个深挖、存储字段、训练代码路径、长文献综述、定义排比、课堂类比故事 |
| 必留 | 最终路线判断、关键验证结果、与产线相关的约束（节拍/可靠/安全/ROI） |
| 必补（可新建） | 双路线对照表；阶段/等级尺（不必抄自动驾驶，可用「L0–Ln / 阶段 1–n」同类尺子）；资源与周期；自家或对标产品落在哪一格 |

### Step 3 — 默认骨架（可按主题改名，勿打乱功能顺序）

```markdown
# [业务词标题：少堆字母缩写]

## 1. [对象]是什么 / 怎么工作（极短）
- 一张模态或组成表即可
- 训练/流程用「三步以内」说完；比喻最多一处且要业务向

## 2. [关键场景]怎么选（决策块，可提到最前）
- 对照表：路线 A vs 路线 B
- 列：过程摘要 | 结果指标 | 周期/人力 | 主要优势 | 仍开放项
- 文末一句站队（或「场景分流：…用 A，…用 B」）

## 3. 我们处在哪（阶段尺）
- 用一张等级/阶段表对齐行业常见说法与**装备/产品形态**
- 格子里写可指认的例子（自家或公开对标），忌空泛未来词堆砌

## 4. 推荐技术路径
- 一句主张（粗体可）
- 主张拆成 2 块机制说明（各一段）
- 多维对照表：推荐路径 vs 备选/前沿路径（架构、实时、数据代价、可靠性、落地痛点）
- 三条以内「为何认可」：探索观望 / 工程现实 / 模块化试错 等——语气务实，避免终局口号

## 5. 案例只证明主张
- 1 个机制拆解表（流程 × 技术 × 作用）即可
- 行业/自家案例点名即可，不展开论文
```

章节可合并或改名，但**决策块不得埋在长原理之后**。

### Step 4 — 语言与呈现

- 标题与一级节名：**业务词 > 准确缩写**（例：具身 / 智能装备；缩写留在首次出现的括号）。
- 数字：**节拍、人天、成功率、样本规模**优先于 TRL、论文 SOTA 表述。
- 表格优先；正文少堆定义。
- 限定句保留：「尚不能…」「当前主路径是…」「前沿继续投入但不主驾产线」。
- 不写空洞排比（「全面赋能」「引领未来」而无主体与条件）。

### Step 5 — 自检清单

- [ ] 主文无数据集字段/开源仓库导览
- [ ] 30 秒能复述主张 + 一个关键数字 + 一个边界
- [ ] 有对照表，且至少一列是代价或周期（或显式「待补」）
- [ ] 阶段尺里能看见「我们/对标」落点
- [ ] 未把实验室演示写成产线常态
- [ ] 新增内容未冒充原文已有的外部事实

---

## 4. 与用户输入的配合

| 用户提供 | 做法 |
| --- | --- |
| 仅长文 md/docx | 按上流程改写；缺决策数字标「待补」并在回复里列出要问的 3–5 个数 |
| 长文 + 验证数据/人天 | **必须**写进决策块，不要留在附录语气里 |
| 要求保留某章深度 | 主文仍短；深度进 `## 附录` 或独立 `*-appendix.md` |
| 要求导出 docx | 改写定稿 md 后调用 `md-to-docx-report` |

输入若是 docx：先用 `docx-to-md-report` 转 md，再对本 skill 输出稿操作。

---

## 5. 输出约定

1. 默认写出新文件：`原名-gm.md` 或用户指定路径；**不要静默覆盖源稿**（除非用户明确要求覆盖）。
2. 回复里用极短段落说明：砍了什么类型的信息、补了什么决策件、哪些数字待补。
3. 不在回复里重复粘贴全文除非用户要求。

---

## 6. 反模式

- 只做删句压缩，结构仍是「第 1–10 章调研体」
- 用更长的正确性辩护代替选型表
- 为了短而删掉唯一能拍板的数字
- 新增「行业趋势」空话段充字数
- 把 `hik_report` 逐句详解当成给总经理的主交付
